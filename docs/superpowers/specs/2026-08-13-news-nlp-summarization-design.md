# news_nlp summarization (c_summary / sector_summary) — design

**Status:** approved, proceeding straight to implementation (user opted to skip a
separate plan-doc/review cycle and have changes committed incrementally instead).

## Goal

Add two new generative-summarization stages to the existing `news_nlp` pipeline
(stage 3 and 4, after the existing sentiment and NER stages):

1. **`c_summary`** — one abstractive summary per article, generated from the
   article's body text plus its already-computed sentiment/entity metadata
   (per `query.sql`'s `source_text` CTE, which is this feature's origin).
2. **`sector_summary`** — one abstractive summary per `(gics_sub_industry, week)`,
   generated by reducing that week's `c_summary` rows for every company in the
   sub-industry into a single sector-performance summary.

## Model

`facebook/bart-large-cnn` (~1.6GB VRAM) for both stages — small, well-proven
on news-style summarization, fits the existing "one model on the GPU at a
time" budget used by the sentiment/NER stages. Input cap is 1024 tokens, so
both stages reuse the existing sentence-aware `chunk_text()` (`chunking.py`)
plus a new **hierarchical reduce**: summarize each chunk, and if there was
more than one chunk, recursively summarize the concatenated chunk-summaries
until they collapse into a single pass.

Alternative considered and rejected: `allenai/led-base-16384` (native 16K
context, no chunking needed) — bigger, slower, less proven for this domain;
rejected in favor of reusing existing, tested chunking infrastructure.

## Schema (`src/news_nlp/db.py`)

```sql
CREATE TABLE IF NOT EXISTS article_summary (
    article_id   INTEGER PRIMARY KEY REFERENCES articles(id),
    summary_text TEXT NOT NULL,
    num_chunks   INTEGER NOT NULL,
    model_name   TEXT NOT NULL,
    processed_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS sector_summary (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    gics_sector       TEXT NOT NULL,
    gics_sub_industry TEXT NOT NULL,
    week_start        TEXT NOT NULL,  -- Monday, ISO date
    week_end          TEXT NOT NULL,  -- Sunday, ISO date
    summary_text      TEXT NOT NULL,
    num_articles      INTEGER NOT NULL,
    num_companies     INTEGER NOT NULL,
    model_name        TEXT NOT NULL,
    processed_at      TEXT NOT NULL,
    UNIQUE (gics_sector, gics_sub_industry, week_start)
);
```

One `sector_summary` row per `(gics_sub_industry, week)` that actually had
qualifying articles that week — sub-industry uniquely determines sector, so
grouping by sub-industry alone is equivalent to grouping by the pair.
Sub-industries with nothing that week get no row (confirmed with user).

## `c_summary` stage (stage 3)

- `db.fetch_pending_company_summaries(conn, limit=None)`: adapts `query.sql`'s
  `source_text` CTE (`http_status_code=200`, `INNER JOIN` to sentiment,
  `INNER JOIN` to entities filtered `score>0.8 AND text NOT GLOB '[0-9]'`,
  `GROUP_CONCAT`), adding `LEFT JOIN article_summary ... WHERE article_id IS
  NULL` to select only unprocessed rows. Returns raw joined columns (ticker,
  company, gics_sector, gics_sub_industry, title, body_text, sentiment label
  + confidence, entities) — the `METADATA/NLP FEATURES/TEXT BODY` template
  text is assembled in **Python**, not SQL: SQLite string literals don't
  interpret `\n` as an escape (unlike Python), so building it in SQL as
  `query.sql` does produces literal backslash-n characters instead of real
  newlines. Assembling in Python fixes that while keeping the same template
  the query specifies.
- **Deliberate behavior carried over from `query.sql`:** because both joins
  are `INNER JOIN`, an article with sentiment but zero qualifying entities
  never gets a `c_summary`. Confirmed as intentional, not changed.
- `pipeline.hierarchical_summarize(text, tokenizer, model, device,
  max_input_tokens=1000) -> (summary_text, num_chunks)`: chunks via
  `chunk_text()`, summarizes each chunk with `model.generate(...)`, and if
  more than one chunk resulted, joins the chunk-summaries and recurses until
  they fit in one chunk.
- `pipeline.run_company_summary_stage(conn, limit=None, on_progress=None)`:
  same shape as `run_sentiment_stage`/`run_ner_stage` — load tokenizer+model,
  loop pending rows, summarize, `db.write_company_summary(...)`, commit per
  row, free GPU when done. Skips loading the model entirely when there's
  nothing pending (existing pattern, tested by
  `test_run_sentiment_stage_reports_empty_progress_without_loading_model`).

## `sector_summary` stage (stage 4)

- `db.fetch_pending_sector_weeks(conn, limit=None)`: joins `article_summary`
  → `articles` for `gics_sector`/`gics_sub_industry`/`pub_date` (falling back
  to `fetched_at` when `pub_date IS NULL`), buckets into Monday-start weeks
  (`date(pub_date, 'weekday 0', '-6 days')`), groups by
  `(gics_sector, gics_sub_industry, week_start)`, keeps only **closed** weeks
  (`week_end < date('now')`, so a partial week is never summarized and later
  need regenerating), excludes tuples already in `sector_summary`.
- `db.fetch_company_summaries_for_sector_week(conn, gics_sector,
  gics_sub_industry, week_start, week_end)`: returns the contributing
  `article_summary` rows (with `company`/`ticker`) for that bucket.
- Reduce-input template (Python-assembled, header written once for the group
  rather than repeated per company/row — the one deliberate deviation from
  the literal per-article template, agreed with user since sector/subsector
  is constant across the whole group):
  ```
  METADATA:
  Sector-{gics_sector}
  Subsector-{gics_sub_industry}

  COMPANY SUMMARIES:
  {ticker} ({company}): {summary_text}
  {ticker} ({company}): {summary_text}
  ...
  ```
- `pipeline.run_sector_summary_stage(conn, limit=None, on_progress=None)`:
  loads BART again (separately from stage 3, freed after — keeps each stage
  self-contained like sentiment/NER), runs `hierarchical_summarize` over the
  reduce-input text, `db.write_sector_summary(...)`.
- `run_pipeline()` becomes: sentiment → NER → company_summary →
  sector_summary, all sequential, one model on the GPU at a time throughout.

## CLI / API

- `cli/news_nlp_cli.py`: no new flags; `--limit` now applies to all 4 stages
  (for stage 4, "rows" means sector-week groups, not articles — documented).
- `apps/news_nlp_api.py`:
  - `/pipeline/run` + `/pipeline/status`: unchanged code, new stage names
    (`"company_summary"`, `"sector_summary"`) flow through automatically via
    the existing `on_progress` callback.
  - `db.get_article_detail()` gains a `"summary"` key (same pattern as
    `"sentiment"`/`"entities"`).
  - New `GET /sectors/summary` (optional `sector`, `sub_industry`,
    `week_start` filters) lists `sector_summary` rows, newest week first.
  - No PATCH/DELETE correction endpoints for summaries — out of scope, not
    requested.
- `src/news_nlp/setup.py`: add the BART model to the `MODELS` prefetch tuple.

## Error handling

- Degenerate/empty chunk list: skip the row, don't write a garbage summary.
- `pub_date IS NULL`: fall back to `fetched_at` for week-bucketing.
- Partial-week safety: `week_end < date('now')` gate, covered above.
- GPU OOM: not a new concern — BART-large-cnn fits comfortably alongside the
  existing one-model-at-a-time discipline.

## Testing

- `db.py`: pending-row selection/exclusion logic for both new fetch
  functions, week-bucketing correctness, `UNIQUE` idempotency on
  `sector_summary`.
- `pipeline.py`: `hierarchical_summarize` with a stubbed tokenizer/model (no
  real BART download in unit tests) — single-chunk passthrough, multi-chunk
  triggers a second (reduce) summarize call; stage functions skip loading
  the model when nothing is pending (mirrors existing sentiment/NER tests).
- `apps/news_nlp_api.py`: new `/sectors/summary` endpoint, `summary` key on
  `/articles/{id}`.
- `tests/news_nlp/conftest.py`'s `ARTICLES_SCHEMA`/`seed_article` need
  `gics_sector`, `gics_sub_industry`, `http_status_code` columns added (the
  real `articles` table already has them, per `src/extractor/db.py`; the
  test fixture is currently missing them).
